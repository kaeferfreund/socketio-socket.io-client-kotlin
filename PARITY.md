# JavaScript parity: evidence and explicit boundaries

Reference: official [`socketio/socket.io`](https://github.com/socketio/socket.io)
commit `aaf2af36ec8ad05910f357a788e0e358bad32738` (client package 4.8.3). The
commit, not a moving version label, identifies the ported implementation.

Every number below comes from the parity validator
(`scripts/check-parity-contracts.py --strict --junit … --summary`), recorded in
[ReviewEvidence/ParitySummary.json](Documentation/ReviewEvidence/ParitySummary.json)
for the commit that added it. CI regenerates the summary on every run; inspect
the run for the commit you plan to ship.

**All 252 supported runtime declarations of the four upstream client packages
have an assertion contract whose Kotlin tests passed in the recorded run (577
passed test executions, 0 failed or skipped; CI run 36216823486, which runs the
Robolectric suite on SDK 34 and 36). The remaining 45 runtime declarations are
reviewed scope boundaries, listed with reasons below. This is test parity for a
defined scope, not proof of every possible JavaScript behaviour.**

## How a row is certified

Each supported row has a contract in
[JavaScriptParityContracts.json](Documentation/JavaScriptParityContracts.json)
that states, in plain language, what the original test asserts, and names the
Kotlin test methods that assert the same. The validator rejects a contract when a
named test file, class or method is missing, when the inventory's `kotlin_tests`
column differs from the contract, or, with `--junit`, when a named test did not
pass in the supplied JUnit reports. It also rejects any failed or skipped test in
those reports. A mapping without a passing run is not evidence.

| Contract kind | Contracts | Meaning |
| --- | ---: | --- |
| `assertion-port` | 176 | The original setup and assertions, ported one to one |
| `native-assertion-equivalent` | 76 | The same assertions with an adapted setup or observation point: a server-side transport kill instead of calling a private JavaScript method, the engine packet observer instead of `packetCreate`, virtual time instead of fake timers, `ByteArray` instead of `Blob`/`ArrayBuffer`. Each contract says what was adapted |
| `kotlin-extension` | 10 | Kotlin-only guarantees without an upstream row (below) |

The 548 distinct test methods named by contracts run as unit tests on virtual time
(in-memory servers from `socketio-testing`), as end-to-end tests against the Node
fixtures in [`fixtures/`](fixtures/README.md) (HTTP, HTTPS, WS and WSS), and as
Robolectric tests for Android.

## Parser differential

[DecoderDifferential.json](Documentation/ReviewEvidence/DecoderDifferential.json)
records `scripts/test-parser-parity.sh`, which runs the pinned JavaScript
`socket.io-parser` and this client's codec on the same inputs: 5,000 generated
valid text and binary packets, 29 malformed or non-canonical headers, and 1,000
packets encoded by Kotlin and decoded by JavaScript (plus 1,000 in the other
direction). The recorded run has zero differences in every category. This is
parser evidence only.

## Original suites

`scripts/test-upstream-clients.sh` runs the unmodified upstream Node suites at the
pinned commit (engine.io-client in its default, `fetch` and built-in WebSocket
modes) and fails when the committed inventory differs from a fresh scan. It tests
the reference implementation, not Kotlin; it proves that the inventoried tests are
the ones that exist and pass upstream.

## Public API

public member of the pinned `socket.io-client` API (the `io()` entry point,

verifies each Kotlin symbol against the `api/*.api` dumps and, in CI, that the
mapped members are exactly those declared in the pinned TypeScript source. Its

## Deliberate differences

These are documented in the [compatibility guide](Documentation/Guides/Compatibility.md)
and do not change a certified assertion:

- WebTransport is not available (above).
- OkHttp compresses WebSocket messages by size (`perMessageDeflateThreshold`); the
  per-message `compress` flag reaches the transport but cannot switch a single
  frame's compression off.
- The reconnection delay stays at `reconnectionDelayMax` after about 1,024 failed
  attempts in a row. JavaScript's backoff turns into `NaN` there (the jitter meets
  an infinite `min × 2^attempts`), and `Math.min(NaN, max) | 0` yields 0 ms, so a
  long outage ends in attempts without delay. Every earlier delay is unchanged.
- A request the HTTP stack refuses to build (a header value OkHttp rejects, a
  malformed URL) fails with `"xhr poll error"`/`"xhr post error"`/`"websocket
  error"`, reported on the next tick like `Request._create` does. JavaScript's
  polling transport skips an invalid extra header instead. The cookie jar ignores
  cookies that are not printable ASCII, since they could not be sent back.
- With `tryAllTransports`, the transport that failed is closed before the next
  one is tried; JavaScript only drops its listeners. Unlike JavaScript, this client
  rejects invalid handshakes, which can arrive on an already open polling
  transport that would otherwise keep polling.
- Polling follows redirects only within the same origin, and the WebSocket
  handshake none: extra headers, cookies and a POST body are never forwarded to
  another host. Node's polling client follows every redirect with the same headers.
- Payloads are `SocketIOValue` trees. Values are converted explicitly
  (`SocketIOValue.of`, kotlinx.serialization); there is no `toJSON()` hook.
- Optional limits (text length, nesting depth, buffered packets, polling body
  size, handshake heartbeat values) are off by default, so the defaults behave like
  JavaScript; `maxAttachments` defaults to 10 as in `socket.io-parser`. A limit
  rejects input instead of truncating it.
